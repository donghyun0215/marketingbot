# Red Team Review — 경쟁팀 시각의 공격 지점
작성: Construction 착수 전 자체 점검

## A. 심사위원/경쟁팀이 때릴 급소 6가지

### A1. "voice-match 됐다는 걸 뭘로 증명하나?" ★최대 취약점
브리프의 합격 기준은 "마케터가 쓴 것과 구분 안 됨"인데, 기존 플랜엔 **측정 수단이 전혀 없었음**.
Baseline 비교 화면은 "우리가 보기엔 우리 게 낫다"는 주장일 뿐 증거가 아님.
- **대응:** Voice Score(0~100) 계산기 도입. 4개 축 — ① 어휘 중첩도 ② 문장 길이 분포(코퍼스 대비) ③ 용어 일관성(제품명 표기 통일) ④ 구조 패턴(도입부/CTA 형식). 생성물에 점수와 근거를 항상 표시.
- **데모 킬러컷:** 블라인드 테스트. 실제 코드프레소 글 2편 + 우리 생성물 1편을 섞어 심사위원에게 "AI가 쓴 걸 골라보세요" 제시. 못 맞히면 그 자리에서 증명 종료.

### A2. "오류 나면 어떻게 되나?" — 심사 제출물 명시 항목인데 플랜에 없었음
브리프에 "고객사명·가격·계약조건이 잘못 나가면 사고"라고 명시됨. 경영진 컨펌이 존재하는 **이유 자체**가 이것.
- **대응:** Fact-Guard 도입. 승인 요청 전 자동 검사 — 금지/주의 항목(고객사 실명, 가격 숫자, 계약 조건, 미검증 수치)을 스캔해 하이라이트 + 위험도 표시. 사람은 "다 읽기"가 아니라 "표시된 곳만 확인"하면 됨.
- **이게 승인 시간 압축의 진짜 논리:** 1~4일이 몇 분이 되는 건 Telegram 버튼 때문이 아니라, **읽어야 할 양이 줄어서**임. 발표에서 이 인과를 명확히 할 것.
- 추가 오류 대응: Telegram 장애 시 웹 대시보드로 폴백(이중 채널), 생성 실패 시 재시도+사람 알림, 모든 상태 전이 audit_log 기록.

### A3. "8단계 중 3개만 한 거 아닌가?"
④편집·⑤업로드·⑥확산이 얇음. 숨기면 Q&A에서 터짐.
- **대응:** 커버리지 맵을 제출물에 명시(REAL/PARTIAL/DESIGN-ONLY + 사유). 정직한 범위 선언이 오히려 신뢰를 얻음. "안 한 것"이 아니라 "일주일 안에 증명 가치가 높은 순서로 골랐다"로 프레이밍.

### A4. "왜 그냥 ChatGPT 안 쓰나?" — 답이 voice 하나뿐이면 약함
- **대응: 3층 방어**
  1. **Voice + Fact 고정** — ChatGPT는 코드프레소 실적/사례를 모르고 지어냄. 우리는 실데이터에 근거.
  2. **학습하는 루프** — ChatGPT는 어제 반려된 이유를 기억 못 함. 우리는 반려 사유가 다음 생성의 제약이 됨.
  3. **요청받지 않아도 돈다** — ChatGPT는 사람이 열어야 시작. 우리 시스템은 매일 알아서 돌고 사람을 부름.
  ▶ 한 줄: "ChatGPT는 사람이 기억해서 써야 하는 도구, 이건 사람을 대신 기억해주는 시스템."

### A5. 성공 정의에 숫자가 없었음 (제출물 필수 항목)
- **대응 (목표 지표):** 경영진 컨펌 1~4일 → 10분 이내 / 성과 취합 주 2시간 → 0분(자동) / 원고 반나절~하루 → 10분 내 초안 / **문의 귀속률 40%(4/10) → 100%** / 톤 일관성: Voice Score 85점 이상만 승인 큐 진입.

### A6. Baseline 비교가 라이브에서 깨질 위험
- **대응:** 비교 결과를 DB에 저장·고정(pre-computed). 영상 촬영도 이 화면으로. 라이브 API 호출 의존 제거.

## B. 논리가 닫히지 않던 루프 4곳 (전부 수정)

기존 플랜은 "플라이휠"이라 부르면서 실제로는 **한 방향 파이프라인**이었음. 데이터가 들어가기만 하고 되돌아오는 경로가 4군데 끊겨 있었다.

### Loop 1 — 콘텐츠 → 문의 귀속이 끊김 ★가장 치명적
실데이터상 문의 10건 중 6건이 출처 불명(확정 1/추정 3/불가 6). 이 상태로 플라이휠을 돌리면 **조회수·클릭 기준으로 주제를 추천**하게 됨.
그런데 코드프레소 기준은 "조회수 잘 나와도 문의 없으면 성과 아님". 즉 우리가 비판하던 실패를 우리가 반복.
- **수정:** 발행 시 콘텐츠별 추적 링크(content_id 삽입) 자동 생성 → 문의 폼이 유입 content_id 수신 → `inquiries.content_id` 저장. 이로써 ⑧에서 리드 기준 성과가 확정되고, 추천이 조회수가 아닌 **문의 기여도** 기준으로 돌아감.
- 원본 데이터의 "GA4 form_submit 미연동" 자백이 이 설계의 근거로 그대로 인용 가능.

### Loop 2 — 반려 사유가 아무 데도 안 쓰임
❌반려 + 사유를 받아놓고 다음 생성에 반영 안 함. 저지먼트 트랙 브리프의 "왜 아닌지 안 적혀 있어서 같은 유형을 또 올린다"와 **동일한 실패**를 오토메이션 쪽에서 재현하는 꼴.
- **수정:** `learned_constraints` 테이블 신설. 반려 사유 → 구조화된 제약으로 변환 → 이후 모든 생성 프롬프트에 주입. 대시보드에 "시스템이 배운 규칙" 목록 노출(= 심사 요구항목 '판단 로그'의 실체).

### Loop 3 — 승인된 콘텐츠가 코퍼스로 안 돌아감
승인된 글 = 사람이 톤을 보증한 글. 최고 품질 학습 데이터인데 버려지고 있었음. Voice Profile이 영원히 고정됨.
- **수정:** 발행 완료 시 `voice_corpus`에 자동 편입(출처: approved). 시간이 갈수록 목소리가 정확해지는 구조.

### Loop 4 — 주제 추천의 성패가 측정 안 됨
추천 → 채택/거절까지만 있고, 그 추천이 실제로 성과를 냈는지 되돌아오지 않음. 추천 로직이 영원히 안 늘어남.
- **수정:** `topic_suggestions.id` → `contents.suggestion_id` → 성과/문의까지 체인 연결. "추천 적중률"을 대시보드 지표로 노출.

▶ 이 4개를 닫아야 비로소 **flywheel**이라고 부를 수 있음. 닫힌 뒤 전체 사이클:
`성과+문의 → 분석 → 주제 추천 → 승인 → 생성(Voice+제약) → Fact-Guard → 승인 → 발행(추적링크) → 성과+문의` ↩

## C. 스코프 방어 (1주일)
- **P0 (없으면 발표 불가):** Voice Engine + Voice Score, Fact-Guard, Telegram 승인 게이트, Baseline 비교, 실데이터 임포트
- **P1 (강하게 만듦):** 4개 루프 폐쇄, 데일리 브리핑, 주제 추천
- **P2 (남으면):** 블로그 스크래핑 자동화(수동 코퍼스로 대체 가능), 채널 포맷 변환기, GEO 체크리스트, UI 폴리시
- 원칙: P0가 끝나기 전엔 P1을 건드리지 않는다.
